# RescueRank final audit

## Verdict

The app starts and its tested core API flows work, but it does **not** fully solve the stated disaster-response problem.
It has a reproducible flood-risk ranking and capacity-aware dispatch, but the result is still a synthetic planning demo, not operational rescue coordination.
Highest-impact gaps: no heatwave mode, no verified real-world alert delivery, the slider does not re-plan resources, and browser-offline behavior was not tested.
Backend API tests and frontend lint/build passed with caveats; the complete backend suite did not pass cleanly because a model download stalled and the no-model fallback test failed.
Scores: Part A **6/10** | B **4/10** | C **4/10** | D **1/10** | E **6/10** | Overall **4.2/10**.

## Scope and evidence notes

Tested the existing Docker app and database without resetting the volume. This was not a genuinely clean database start. The prescribed `docker compose up --build -d` completed earlier in this audit; all three services then reported healthy. Later, a final `docker compose ps` attempt failed with `permission denied while trying to connect to the Docker API` on the Windows named pipe, so that later attempt could not independently re-confirm current health. No browser automation/browser executable was available, so visual interactions, browser console, and offline mode are explicitly unverified. API changes below were made against the existing synthetic database to perform the requested E2E checks; the database was not reset afterward. No application file was edited during the audit. The working tree already contained unrelated user changes before this report.

### Startup, endpoints and checks actually run

- `docker compose up --build -d` — completed; frontend/backend images built, DB healthy, frontend/backend started. Follow-up `docker compose ps` showed `rescuerank-db`, `rescuerank-backend`, and `rescuerank-frontend` healthy (ports 5433, 8000, 3000 respectively). Existing database volume means this does not prove a clean empty-database start.
- `GET http://localhost:8000/api/v1/health` — 200, `{"status":"healthy","database":"connected","city":"Karachi, Pakistan","hazard":"Urban & Riverine Flooding","synthetic_data":true}`.
- HTTP GET — 200 for `/`, `/priorities`, `/resources`, `/reports`, `/field`, `/prepositioning`; API GET — 200 for `/health`, `/zones`, `/waterways`, `/priorities`, `/reports`, `/resources`, `/assignments`, `/prepositioning/timeline`, `/openapi.json`, and one household explanation. Tested POSTs `/reports`, `/assignments/optimize`, `/simulate/resource_conflict`, `/simulate/advance_forecast_3h`, and PATCH `/assignments/{id}/override` returned 200. No 5xx was observed among these requests; this is not an exhaustive fuzz/test of every parameter or route.
- `docker compose exec -T backend pytest -q tests/test_api.py` — **12 passed**.
- `docker compose exec -T backend pytest -q tests/test_scoring.py tests/test_routing.py` — **16 passed**.
- `docker compose exec -T backend pytest -q tests/test_pipeline.py -k "not haversine"` — **5 passed, 1 deselected**.
- `docker compose exec -T backend python -m pytest` — failed because pytest is not installed in the production runtime image. Pytest and pytest-asyncio are documented as dev extras in `backend/pyproject.toml`; for the test runs above, they were installed into the disposable running backend container only (no project file changed).
- Full `pytest -q` — stalled on `test_haversine_distance_and_clustering` while attempting to download `paraphrase-multilingual-MiniLM-L12-v2`; interrupted. Re-running that test with the model getter forced to `None` failed its paraphrase-match assertion (`match is None`). Thus the complete suite is **not** green/offline reproducible.
- `docker build --target builder -t rescuerank-audit-frontend:local .` from `frontend` — build succeeded. `docker run --rm --entrypoint sh rescuerank-audit-frontend:local -c "npm run lint"` — passed with four React hook dependency warnings in field, home, priorities and OfflineBanner. Docker build ran `npm run build`; Next.js compile/type-check/build succeeded for all six routes.
- Browser availability check (`Get-Command msedge,chrome,chromium,firefox`) — no browser found. No browser console or manual visual test was performed.

## Failures and risks (ranked by severity)

1. **Critical operational limitation — synthetic people and approximate hazards.** Demo household locations, vulnerability and forecasts are not real verified data. A judge could mistake a ranking for real evacuation advice; it must never direct an actual rescue.
2. **High — no heatwave or multi-hazard operation.** It fails an explicit breadth criterion and requires more than configuration to extend.
3. **High — alerts are not proven delivered.** The forecast simulator reported two alerts, while notifier logs stated Telegram/WhatsApp credentials were missing and sends were simulated. Judges may see a success state and infer delivery.
4. **High — planner scope mismatch.** Only 25 candidates were optimized from a 600-household ranking; flood slider changes ranking but not dispatch plan. The dashboard and resource board can therefore represent different scenarios.
5. **High — report conflict/duplicate validation incomplete.** Idempotency replay worked, but actual contradictory spatial reports were not demonstrated; model download stalls tests and the no-model paraphrase fallback test fails.
6. **Medium — ranking explanation inconsistency.** The single-household explanation endpoint omitted inputs used by the list score; observed 41.8 versus 49.5 for the same household. This undermines trust in “why this person first.”
7. **Medium — shelters are not demand-balanced.** Occupancy is shown, but no expected evacuee load or actionable overflow warning was verified.
8. **Medium — offline behavior unverified.** Code exists, but no browser test proved shell/data availability, queued report persistence, or once-only sync.
9. **Medium — UI verification gaps.** No browser console, mobile, keyboard, contrast or screen-reader inspection was possible; frontend lint emits four hook dependency warnings.
10. **Low/medium — runtime test tooling.** Production backend image lacks pytest; developer extras work only after explicitly installing them into a test environment/container.
